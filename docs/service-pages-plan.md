# Service pages enhancement plan

## Direction

Give each “What I can help you build” card a dedicated page with useful service detail, relevant selected work, practical answers, and a contextual chat action. Reuse the selected-work visual language and illustration workflow while keeping service offers distinct from completed project stories.

Preserve high-resolution Blender renders as source assets. Derive optimized page images and lightweight web models from the original scenes, following the selected-work approach: an immediate responsive still, with optional subtle mouse-responsive 3D on suitable desktop devices. Mobile, reduced-motion, constrained connections, and unavailable graphics use the still. Essential content never depends on graphics or chat.

This is the single public planning document for this work. Detailed source reviews, captures, measurements, and phase notes belong in the ignored `docs/local/` folder. Update this document as decisions change; review each phase before proceeding.

## Page structure

- A clear service headline, short explanation, and hero illustration.
- Problems the service solves and the people or teams it suits.
- Typical deliverables and the decisions that shape scope.
- How an engagement moves from understanding the problem through delivery and handover.
- Relevant published selected-work examples as evidence.
- Practical questions and concise answers using the shared disclosure component.
- A contextual chat CTA that identifies the service being discussed.

Keep useful information in server-rendered HTML. Retain the site's typography, selective geometric patterns, gold icon actions, responsive spacing, keyboard access, and Motion/reduced-motion behavior. Label artwork “Conceptual illustration”; it does not depict a shipped client product. Avoid invented outcomes, pricing, timelines, testimonials, or guarantees. Service pages should add useful detail beyond the homepage cards.

## Asset workflow

The current homepage images are 880 × 480 JPEGs in `public/services/`, generated by `scripts/render-services.py`. They are delivery assets, not high-resolution masters. Re-render the original scenes at higher resolution rather than enlarging those JPEGs.

- Retain editable `.blend` scenes and lossless master PNGs under `assets/services/<theme>/`, separate from public web assets. Aim for at least 2800 pixels wide; review framing before fixing the final dimensions.
- Preserve the existing recognizable compositions, colors, and service themes. Adjust framing for a larger hero only where needed.
- Generate desktop and mobile WebP images with deliberate crops and declared dimensions. Start with the selected-work budgets: 1400-pixel desktop image below 80 KB and 768-pixel mobile image below 35 KB. Record and review any justified exception.
- Export any interactive version from the actual Blender geometry. Do not simulate a real model by panning a flat image. Simplify materials and geometry for the web; target a self-contained GLB below 320 KB per service.
- Reuse the optional demand-rendered viewer and its loading, graphics-failure, pause, and route-change behavior where appropriate. Keep the still visible until the model renders successfully.
- Serve only optimized assets from `public/services/`; use reproducible scripts and document dimensions, crops, file sizes, and rebuild commands.
- Review the image and model together so switching between them does not visibly change the composition. High-resolution masters must never download as part of a normal page visit.
